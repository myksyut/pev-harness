# v4.2 設計: Fable orchestrator + model tiering の費用モデル

> Goal: **Fable 5 をオーケストレーターに、 計画・実行を他の Claude model に委譲してトークンコスト (金額ベース) を抑える**。 性能はハーネスなしの Claude Code (Opus 4.8 単独 session) と同等以上を維持する。

## 1. 前提: 単価表 (Claude API、 cached 2026-06-24)

| Model | Input $/MTok | Output $/MTok | 役割 (v4.2) |
|---|---|---|---|
| Claude Fable 5 (`claude-fable-5`) | 10.00 | 50.00 | **Orchestrator (main session)** |
| Claude Opus 4.8 (`claude-opus-4-8`) | 5.00 | 25.00 | Planner |
| Claude Sonnet 5 (`sonnet` alias) | 3.00 (intro 2.00 〜2026-08-31) | 15.00 (intro 10.00) | Triage / Executor / Verifier |
| Claude Haiku 4.5 | 1.00 | 5.00 | (不採用、 §6 参照) |
| OpenAI Codex CLI (ChatGPT subscription) | — | — | Executor default (API 従量課金なし) |

**核心の制約**: Fable は Opus の **2 倍単価**。 「Fable を使えば安くなる」 は成立しない。 成立するのは「**Fable を薄い指揮層に限定し、 token 量の重い phase を安い層へ委譲する**」 構造のみ。 これが v4.2 の設計そのもの。

## 2. 構成 (v4.1 → v4.2 の差分)

| Layer | v4.1 | v4.2 | 変更理由 |
|---|---|---|---|
| Orchestrator (main session) | opus-4-8 / xhigh | **fable-5 / high** | 長時間・多 round の pipeline 駆動 (`/goal` retry 判断、 Gate 判定、 escalation) は Fable の long-horizon 特性が最も効く層。 effort は xhigh → high に下げ output token を削減 (Fable は low effort でも従来 model の xhigh 相当、 公式 migration guide) |
| Triage | sonnet / low | sonnet / low | 据え置き |
| Planner | opus / xhigh | opus / xhigh | 据え置き (質問返し品質はハーネスの value そのもの、 downgrade しない) |
| Executor | sonnet / high (default codex 委譲) | 同左 | 据え置き |
| Verifier | sonnet / xhigh | sonnet / xhigh | 据え置き |

phase の実体は一切変えていないため、 **phase 品質は v4.1 と同一**。 変わるのは指揮層の model のみ。

## 3. コスト規約 (invariant)

Fable orchestrator が成立する条件は「orchestrator が薄いこと」。 `rules/pev-conventions.md` §7 に明文化した:

1. orchestrator は artifacts (triage.json / plan.md / verify.json) の parse と dispatch のみ。 **実装 file を Read しない**
2. orchestrator turn で **code 変更・test 実行をしない**
3. agent frontmatter の model を fable へ引き上げない (fable は orchestrator 専用 tier)
4. orchestrator の token 消費は task 全体の **15% 以下** を目安とする

## 4. 費用試算 (中規模 feature task、 Mode A = plan_required)

token profile の仮定 (harness-effect dog food の実測オーダーに基づく概算、 uncached 上限):

| 作業 | Input | Output |
|---|---|---|
| Orchestration (routing / Gate / `/goal` / recap) | 50k | 3k |
| Triage | 10k | 1k |
| Plan | 60k | 8k |
| Execute | 120k | 15k |
| Verify | 80k | 6k |

orchestrator 比率 = 53k / 353k ≈ **15%** (規約の目安値と整合)。

### 比較

| 構成 | 内訳 | 合計 |
|---|---|---|
| **Baseline: ハーネスなし Claude Code** (Opus 単独 session、 全作業を 1 context に累積 ≈ input 600k / output 33k) | 0.60M×$5 + 0.033M×$25 | **$3.83** |
| v4.1 harness (orch=opus、 executor=codex) | orch $0.33 + triage $0.05 + plan $0.50 + exec $0 + verify $0.33 | **$1.20** |
| **v4.2 harness (orch=fable、 executor=codex)** | orch $0.65 + triage $0.05 + plan $0.50 + exec $0 + verify $0.33 | **$1.53** |
| v4.2 harness (orch=fable、 executor=claude sonnet) | 上記 + exec $0.59 (codex なし環境) | **$2.11** |

- v4.2 (codex) は **baseline 比 約 −60%**、 claude executor fallback でも **約 −45%**
- v4.1 比では orchestrator premium (+$0.33/task) を払う。 これは「retry round 判断・escalation・Gate 判定を最上位 model が行う」 ことへの対価で、 baseline 比の削減幅 (−$2.30) に対し十分小さい
- plan_skip path (Mode B) では Plan $0.50 が消え、 さらに安くなる
- prompt caching (cache read 0.1×) は全構成に等しく効くため相対順位は不変。 Sonnet 5 intro 価格 (〜2026-08-31) 適用時はさらに 1/3 減

### 感度分析: なぜ「orchestrator thin」 が invariant か

orchestrator が実装 file を自分で読み始めて input が 300k に膨らんだ場合:

```text
fable orch = 0.30M×$10 + 0.01M×$50 = $3.50 → 合計 $4.4 > baseline $3.83
```

**規約 1 つ破るだけで baseline より高くなる**。 15% ルールはこの反転点から逆算した guardrail。

## 5. 性能同等性の論拠

1. **phase 実体は不変**: plan / execute / verify の model・effort・prompt は v4.1 のまま。 成果物品質を決める層に変更なし
2. **指揮層は strictly upgrade**: Fable 5 は公式に「most capable widely released model、 long-horizon agentic work 向け」。 orchestrator の仕事 (retry 打ち切り判断、 FAIL 時の re-plan 指示の質、 escalation 判断) は long-horizon 判断そのもの
3. ハーネス構造自体の効果 (質問返し / 独立 verify / retry) は harness-effect-v1〜v18 で実証済

## 6. 採らなかった選択肢

- **Triage を Haiku 4.5 に**: 単価は 1/3 だが Haiku は `effort` parameter 非対応 (400 error)。 frontmatter effort 継承と衝突する risk に対し、 Triage は元々 1 turn / 小 context で削減額が数 cent 未満。 見送り
- **Planner を Sonnet 5 に downgrade**: −$0.20/task 程度の削減に対し、 質問返し (= ハーネスの value proposition) の品質 risk が釣り合わない。 見送り
- **Orchestrator effort を xhigh 維持**: Fable は effort が低くても従来 model 超の判断品質 (公式 migration guide)。 orchestrator の output は数 k token だが $50/MTok なので high に下げる

## 7. Degrade path

| 状況 | 挙動 |
|---|---|
| Fable が使えない org (ZDR = zero data retention。 Fable は 30-day retention 必須で 400) | `.claude/settings.local.json` で `"model": "claude-opus-4-8"` に override (= v4.1 相当) |
| Fable の safety classifier refusal (`stop_reason: refusal`) | orchestrator 用途 (coding pipeline 駆動) では実質発生しない想定。 発生時は同上 override |
| codex 未認証 | 従来通り executor が claude native に自動 degrade (v3.5.0+) |

## 8. 検証計画 (harness-effect-v19、 実機 dog food)

CLAUDE.md §1 の原則通り release 後に実機 invoke で検証する。 本環境 (remote、 claude CLI subprocess 認証なし) では実行不可のため、 ローカルで:

1. **A/B 同一 task**: examples/sample-project の form fixture に同一 feature task を投入
   - A: `claude --model claude-opus-4-8 -p "<task>"` (ハーネスなし baseline)
   - B: `/pev-harness:pev <task>` (v4.2、 `--settings '{"outputStyle":"default"}'` 必須)
2. **計測**: stream-json の `usage` fields (`input_tokens` / `output_tokens` / cache 系) を model 別に集計し、 §1 単価表で金額換算
3. **判定**: (a) B の verify.json が PASS かつ独立 `npm test` exit 0、 (b) B の金額 < A の金額、 (c) orchestrator token 比率 ≤ 15%
4. findings は本 file に追記し、 反転があれば §3 の規約 or §2 の構成を修正する
