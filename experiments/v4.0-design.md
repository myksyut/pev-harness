# v4.0 設計 — 公式 primitive への再配置 (grill-me / goal / loop の上に乗る薄い orchestration + domain pack)

**Status**: Design draft + PoC 計画 (user-approved direction: 「再配置を実験する」)
**Predecessor**: v3.7.3 (released)
**Reference**: [/goal docs](https://code.claude.com/docs/ja/goal) + [grill-me SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md) + [v3.0-design.md](v3.0-design.md)

## 0. 動機 — primitive が pev の自前実装を追い越した

Claude Code v2.1.139+ で `/goal` (完了条件まで自走) が公式 primitive 化、 grill-me skill (要件を質問攻めで引き出す) が community に登場した。 これらは pev-harness が v3.0 で苦労して自前実装した層と **機構レベルで同型**。 「全面置換」 ではなく 「どの層を primitive に明け渡し、 どの層に集中するか」 の **再配置** が論点。

## 1. 重なりの地図

| pev-harness の層 | 公式 primitive | 重なり | 注釈 |
|---|---|---|---|
| Plan の質問返し (v3.0 で「user の頭の中の spec を引き出す」 と再定義) | **grill-me** | ◎ ほぼ同一 | grill-me は逐次 decision-tree (1問ずつ + 推奨答え + コードで答えられるものは自分で調べる)。 pev の `AskUserQuestion` まとめ出しより洗練の可能性 |
| Plan の AC (Acceptance Criteria) | `/goal` の condition | ○ | AC ≒ 完了条件。 4000 字制約あり |
| Execute ↔ Verify の retry orchestration | `/goal` の自走ループ | ◎ | pev 自前保守 vs 公式が面倒を見る |
| **Verify (独立 agent が実 test を実行)** | `/goal` の evaluator | **✗ 決定的に違う** | §3 参照 |

## 2. 再配置後の flow (案)

```
┌──────────────┐
│  User input  │
└──────┬───────┘
       ▼
┌──────────────────────────┐
│  要件引き出し層            │  ← grill-me 寄せ (逐次質問 + 推奨答え)
│  (旧 Plan の質問返し部分)  │     明確なら skip (= 旧 Triage plan_skip 相当)
└──────┬───────────────────┘
       ▼
┌──────────────────────────┐
│  自走ループ                │  ← /goal 駆動
│  Execute → verify → ...    │     condition = 「独立 verifier が PASS を報告」
└──────┬───────────────────┘
       ▼
┌──────────────────────────┐
│  独立 Verify + domain pack │  ← pev に残す本体価値 (§3 / §4)
│  実 test 実行 / Codex / E2E│     /goal evaluator では代替不能
└──────────────────────────┘
```

### 各層が誰の責務になるか

| 層 | v3.x (現状) | v4.0 (再配置案) |
|---|---|---|
| 要件引き出し | planner agent の質問判定 | grill-me 的 skill (逐次質問) |
| 自走 retry | commands/pev.md の orchestration | `/goal` (公式) |
| 完了判定 (ループ条件) | verifier → planner 差し戻し | `/goal` evaluator が verifier の報告を読む |
| **独立検証 (実 test)** | **verifier agent** | **verifier agent (維持)** |
| domain (Linear / E2E / QA技法 / Codex) | 各 skill | 各 skill (維持) |

## 3. 最大論点 — `/goal` evaluator は「ツールを呼ばない」

`/goal` docs 明記:

> 評価器は…独立してコマンドを実行したりファイルを読み取ったりしないため、 Claude 自身の出力が実証できるものとして条件を作成します

つまり `/goal` の Haiku evaluator は **会話に表示済みの内容しか判断できない**。 一方 pev verifier は **別 context の独立 agent が実 test を走らせて** AC を検証する。 ここを `/goal` に丸投げすると 「Claude が test 通ったと自己申告 → Haiku が鵜呑み」 となり、 **pev の核心価値 (独立検証) が崩れる**。

### 解決の方向 — 分業

独立検証は verifier agent が担い、 ループ判定だけ `/goal` に委ねる:

```
[verifier agent が npm test を実行]
        ↓
[verify.json + 結果サマリを「会話に明示出力」]
        ↓
[/goal の Haiku evaluator がその出力を読む]
        ↓
[PASS と読めれば goal 達成 / FAIL なら次ターン (= Execute 再実行)]
```

キモは **「verifier の実行結果が会話に証跡として乗る」 こと**。 それを前提に `/goal` の condition を組む。

#### PoC 補正 (F_v18_5) — verifier の dispatch は明け渡さない

harness-effect-v18 実験 B で判明: condition に「verifier が検証せよ」 と書くだけでは **agent 分離は保証されない**。 evaluator は会話テキストしか読めないため、 executor が同一 context で test を回して `verified_by: verifier-agent` と **自称** すれば、 それを信じてしまう (実験 B で Task dispatch=0 のまま PASS 判定)。

→ 真の独立検証 (別 context・別 agent・場合により別 model) を保つには、 **verifier を別 Task として起動する dispatch を pev の commands orchestration が握り続ける**。 `/goal` には「ループを継続/停止するか」 の判定だけ委ね、 「各ターンで verifier subagent を起動する」 ところは明け渡さない。 = 「機構は借りる、 独立検証の dispatch は持つ」。

### 完了条件 (condition) の設計

condition の良し悪しが再配置の自走層の成否を直接決める。 evaluator は会話しか読めないので、 **verifier が会話に出した何を根拠に PASS と判定させるか** を明示的に書く。 docs の「効果的な条件」3要素 (1つの測定可能な終了状態 / 述べられたチェック / 重要な制約) + 暴走防止句を満たす形で確定した:

```text
# /goal condition の設計指針 (docs の「効果的な条件」より):
#  - 1 つの測定可能な終了状態 (test 結果 / exit code / verify.json の verdict)
#  - 述べられたチェック (Claude = verifier がそれをどう証明すべきか)
#  - 重要な制約 (その過程で壊してはいけないもの)
#  - 暴走防止句 (例: or stop after N turns)

PEV_GOAL_CONDITION = """
The pev verifier agent (not the executor's self-report) has independently run
`npm test`, and the conversation shows BOTH the raw `npm test` output exiting 0
AND a verify.json verdict of PASS. The verifier — not the implementer — must be
the one who produced that evidence in the conversation. Constraint: no
pre-existing validator or test file may be modified, only additions. Stop and
hand back control after 10 turns if this is not yet shown.
"""
```

**設計の肝 (= 自己申告事故の防止)**:

1. `(not the executor's self-report)` / `The verifier — not the implementer — must be the one who produced that evidence` で、 evaluator が executor の「通った」を根拠に止めるのを明示禁止。 独立 verifier の証跡のみを PASS 根拠に強制。
2. `BOTH the raw npm test output exiting 0 AND a verify.json verdict of PASS` — 二重根拠 (生 test 出力 + 構造化 verdict)。 どちらか一方の捏造では止まらない。
3. `Constraint: ... only additions` — 既存 test を壊して緑にする退行を禁止 (docs の「重要な制約」)。
4. `Stop ... after 10 turns` — 暴走防止句。

英語で書いたのは `/goal` evaluator の default が Haiku で、 docs の例も英語のため (literal instruction-following の安定性を優先)。

## 4. pev に残す本体価値 (= primitive で再現不能)

1. **独立検証**: verifier が別 context・別 agent・場合により別 model (Codex dual-review) で実 test 実行。 `/goal` evaluator (tool 呼ばない・同 provider Haiku) では原理的に不可。
2. **永続 artifacts**: plan.md / verify.json による phase 間受け渡し・再開・Linear sync。 `/goal` は session-scoped な Stop hook wrapper に過ぎない。
3. **domain pack**: QA 6 技法 (pev-test-design) / Playwright E2E / Codex external review / team-conventions 注入 / Linear。 primitive の組み合わせでは出てこない。

CLAUDE.md §9 「車輪の再発明をしない / ミニマル原則」 と整合する痩せ方。

最も不確実 = 「§3 の分業が技術的に成立するか」。 これを最小コストで先に潰す。

| step | 内容 | 観察点 |

## 6. 不確実性 / 残課題

- **evaluator が verify.json の中身を会話越しに正しく読めるか**: → **正直パスは実証済** (harness-effect-v18 / F_v18_1)。 verifier が会話に出した PASS を根拠に自走が止まった
- **自己申告で誤って止まるリスク**: → **検証済 (F_v18_3 / F_v18_5)**。 condition の「生 test 出力 exit 0 を出せ」 圧力は実 test 実行を強制できた (= 手抜き停止は防げた、 F_v18_3)。 だが agent 分離は condition では保証されず、 executor の verifier 自称を evaluator は見破れない (F_v18_5)。 → 結論: ループ判定は `/goal`、 verifier の別 Task dispatch は pev orchestration が握る (§3 PoC 補正)
- **grill-me を dependency にするか内製するか**: → **内製化が妥当 (実体確認済)**。 grill-me SKILL.md の本体は frontmatter + 6 行のみ (「共有理解まで徹底インタビュー / design tree を1枝ずつ / 各質問に推奨答え / 1問ずつ / コードで答えられるなら探索」)。 external dependency にするほどの実装量はなく、 pev の planner skill に「逐次質問 mode」として数行で取り込める。 v3.0 の F1 scope 限定 (UI / spec 補完は質問必須) と組めば、 pev 版は「どの領域で質問を強制するか」 の domain 知識を上乗せした上位互換になりうる
- **breaking change**: `/goal` 必須 = Claude Code v2.1.139+ に bump (現状 v2.1.156 必須なので影響なし)
- **既存 commands/pev.md の orchestration をどこまで /goal に明け渡すか**: 全面 vs 一部

## 7. PoC で確定した点 / 残る判断

**確定 (harness-effect-v18)**:

1. 再配置の大方針は妥当 (要件→grill-me 内製 / 自走→`/goal` / 独立verify dispatch + domain→pev)
2. 自走の機構 (ループ継続/停止判定) は `/goal` に明け渡せる (F_v18_1)
3. ただし verifier の **別 Task dispatch は pev orchestration が握り続ける** (F_v18_5) — `/goal` への全面丸投げは agent 分離を壊す
4. grill-me は内製化が妥当 (6 行、 F_v18_4)

**残る判断 (本実装に進む前に)**:

- A. v4.0 を実装 release に進めるか (= commands/pev.md を `/goal` 駆動 + verifier dispatch 維持に改修、 planner に grill-me 的逐次質問 mode 追加)
- B. それとも追加 PoC を先にやるか (例: `/goal` 駆動下で pev commands が毎ターン verifier subagent を Task 起動する orchestration の実機検証)
- C. `/goal` 必須化に伴う必須 version の再確認 (現状 v2.1.156 必須 ≥ `/goal` の v2.1.139 なので問題なし)
