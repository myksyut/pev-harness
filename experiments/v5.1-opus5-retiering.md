# v5.1 設計: Opus 5 リリースを受けた model tiering 再検討

> Goal: **Opus 5 (2026-07 リリース) を踏まえて v4.2 の model tiering を再評価し、 orchestrator default を決定する**。 v4.2 の費用モデルと harness-effect-v19 の実測 ([v4.2-fable-orchestrator-cost.md](./v4.2-fable-orchestrator-cost.md)) の続編。

## 1. 前提: 単価表の更新 (Claude API、 2026-07-28 時点)

| Model | Input $/MTok | Output $/MTok | v4.2 での役割 | v5.1 での役割 |
|---|---|---|---|---|
| Claude Fable 5 (`claude-fable-5`) | 10.00 | 50.00 | Orchestrator (default) | **opt-in tier** (settings.local.json override) |
| **Claude Opus 5 (`claude-opus-5`)** | **5.00** | **25.00** | (未リリース) | **Orchestrator (default) + Planner (alias 経由)** |
| Claude Opus 4.8 (`claude-opus-4-8`) | 5.00 | 25.00 | Planner (alias 経由) / degrade path | (現行 CLI では alias 解決先から外れた) |
| Claude Sonnet 5 (`sonnet` alias) | 3.00 (intro 2.00 〜2026-08-31) | 15.00 (intro 10.00) | Triage / Executor / Verifier | 同左 (据え置き) |
| OpenAI Codex CLI | — | — | Executor default | 同左 (据え置き) |

Opus 5 の要点 (公式 model catalog / migration guide より):

- **Opus 4.8 と同価格のドロップイン後継**。 最も強化された領域は deep reasoning / **agentic / long-horizon work** — v4.2 で Fable を選んだ理由 (long-horizon 判断) の主戦場
- **retention 制約なし** (Fable は 30-day retention 必須で ZDR org は 400)。 rate limit は Opus 4.x と別バケット
- 注意点: (a) デフォルトで応答が長くなる傾向 (F_v19_10 の「饒舌さが単価差を相殺する」 機構の再来 risk)、 (b) thinking がデフォルト on、 (c) safety classifier による `stop_reason: refusal` が Fable 同様に存在 (coding pipeline 駆動では実質非発生想定)

## 2. 事実確認: alias 解決の実態 (docs との乖離)

agent frontmatter の `model: opus` / `model: sonnet` は **CLI v2.1.219+ で Claude 5 世代に自動解決される** (公式 doc 裏取り済):

| Alias | v2.1.156〜218 | v2.1.219+ (現行) |
|---|---|---|
| `opus` | Opus 4.8 | **Opus 5** |
| `sonnet` | Sonnet 4.6 → 5 | **Sonnet 5** |

つまり **planner は docs 更新前から既に Opus 5 で動いていた** (v5.1 での変更は「事実の追認 + docs の実態追随」)。 provider 依存に注意: Bedrock 等では alias の解決先が異なるため、 pin が必要な環境のみ full ID を明示する。

## 3. 判断: orchestrator を Opus 5 に切替 (Fable は opt-in へ)

v4.2 の F_v19_10 で選定軸は 3 点に整理されていた。 Opus 5 リリース後の評価:

| 選定軸 (F_v19_10) | v4.2 時点 (fable vs opus-4-8) | v5.1 時点 (fable vs opus-5) |
|---|---|---|
| (a) retry/escalation 判断品質 | fable に実戦実績 (mc-sp round 2)、 opus 側は未対決 | Opus 5 は 4.8 から「deep reasoning / agentic」 が step-change。 gap は縮小と評価 |
| (b) ZDR org 互換 | opus のみ (degrade path が必要) | **Opus 5 の一方的優位** (retention 制約なし、 default が全 org で動く) |
| (c) long-horizon 余裕 | fable | Opus 5 の主戦場が long-horizon (公式)。 gap は縮小と評価 |

コスト面は F_v19_10 で「opus-tier orchestrator は fable と総額等価 (饒舌さが単価差を相殺)」 が実測済みのため、 切替の期待値は「コスト同等以下 + 判断品質は 4.8 等価線より上 + ZDR 互換」。 default を切り替え、 Fable を settings.local.json での opt-in tier に反転する。 詳細な判断ログ: SPEC.md ADR-011。

### v5.1.0 の tiering (確定)

| Layer | Model | Effort | v4.2 からの変更 |
|---|---|---|---|
| Orchestrator (main session) | `claude-opus-5` | high | **fable-5 → opus-5** |
| Triage | `sonnet` (現行 Sonnet 5) | low | なし |
| Planner | `opus` (現行 Opus 5) | xhigh | なし (alias 解決の追認のみ) |
| Executor | `sonnet` (default codex 委譲) | high | なし |
| Verifier | `sonnet` | xhigh | なし |

### 採らなかった選択肢

- **Fable default 維持**: 単価 2 倍を正当化していた long-horizon 優位が Opus 5 で縮小し、 ZDR 非互換の非対称 (degrade path 維持コスト) だけが残る。 opt-in で残すことで「最上位判断が必要な長大 pipeline」 用途は保全
- **planner を `claude-opus-5` に明示 pin**: alias 追随 (次世代リリース時に自動で恩恵) を優先。 provider 差異で pin が必要になった時点で再検討
- **planner を Opus 4.8 に pin して据え置き**: 質問返し品質への Opus 5 の影響を懸念する保守案だが、 alias は既に Opus 5 に解決されており「据え置き」 は実際には downgrade pin。 dog food で挙動監視する方を選択
- **Sonnet 層 / executor の変更**: Sonnet 5 は既に alias 経由で適用済み。 Haiku 4.5 は effort 非対応で v4.2 と同じ理由で見送り

## 4. 監視項目 (dog food / 以後の harness-effect)

1. **orchestrator token 比率**: Opus 5 の「応答が長くなる傾向」 が §7 の 15% 目安を悪化させないか (緩和策: 返答要約契約 + pev.md 薄型化は維持済み)
2. **planner 質問返し品質**: Opus 5 の literal-following 強化が確認質問の質に与える影響 (interactive dog food で確認)
3. **plan.md の長文化**: Opus 5 は「書き出す deliverable が長くなる傾向」 が公式に明記。 plan.md が冗長化するようなら planner prompt に長さ規律を追加
4. **retry/escalation の実戦品質**: FAIL → retry round での orchestrator 判断 (F_v19_10 で fable 側にのみ実績があった軸)

## 5. 検証結果 (v51-dogfood、 2026-07-28)

お題: form fixture への validatePostalCode 追加 (Goal/Constraints/AC 明示、 headless `--model claude-opus-5` + `--settings '{"outputStyle":"default"}'` + bypassPermissions)。

| 指標 | 値 |
|---|---|
| pipeline | **full 完走**: Triage (plan_skip 正判定、 ambiguity_signals 空) → Execute (codex → 途中切断 → Claude native fallback) → **独立 verifier PASS** (28/28 tests、 AC 3/3、 node one-liner での独立検証込み) |
| 独立再確認 | 検証者とは別に `npm test` を手元で再実行 → exit 0 (28 passed) |
| 金額 (CLI total、 model 合算一致) | **$2.48** — opus-5 $1.18 (out 12.6k / cacheR 645k) + sonnet-5 $1.29 (out 24.9k / cacheR 1.30M)。 **fable 消費 $0** (= orchestrator が opus-5 で動作している確認) |
| 実 wall clock | 653 秒 (Stop hook 計測) / CLI result 186 秒 (最終 turn) |
| telemetry | session.json 全 field 記録 (phases object / tokens / user chat log)。 recap.log は Gate 判定を全記録 |

### Findings

- **F_v51_1 (version 同期漏れ)**: session.json の `harness_version` が commands/pev.md の jq 雛形にハードコードされており ("5.0.0" のまま記録)、 release 手順 (CLAUDE.md §5 [5]) の version 同期対象から漏れていた。 → 対処済み: pev.md を 5.1.0 に更新 + §5 手順に同期対象として明記
- **F_v51_2 (codex 途中切断の graceful fallback 実戦確認)**: codex が src/validation.js のみ編集して output JSON なしでプロセス終了 → executor が `fallback_reason: codex_incomplete` を execute.log に記録し、 残り (test file) を Claude native で完遂。 v3.5.0 で設計した degrade path の実戦初確認
- **orchestrator 比率**: opus-5 のコストシェア 48% ($1.18/$2.48)。 小規模 plan_skip task では固定 overhead (command context + dispatch) が支配的で 15% 目安を超えるのは既知傾向 (F_v19_2/F_v19_8 と同型、 v19 では大規模 task で 26〜37%)。 model 切替起因の悪化ではない (v19 の fable も同構造)。 turn 統合による削減は引き続き次 release 候補
- **Opus 5 の饒舌 risk (§4 監視項目 1)**: orchestrator 出力は 12.6k tokens。 v19 の opus-4-8 orchestrator (≈19k) より小さく、 F_v19_10 で懸念した「饒舌さによる相殺」 の悪化は今回のサンプルでは観測されず (要約契約 + 薄型化の効果が Opus 5 でも機能)

## 6. harness-effect-v20: 「verifier も Opus 5 にすべきか」 の A/B (2026-07-28)

「Opus 5 は安いのだから全部 Opus 5 でよいのでは」 という問いへの実測回答。 §3 の据え置き判断 (Sonnet 層は変更なし) のうち、 最も判断品質が効きうる **verifier** を分離検証した。

### 設計 (シードバグ判別器)

executor 分散を排除するため full pipeline ではなく **同一のバグ入り workspace に対する verify 単体** で比較する:

- form fixture に validatePostalCode を実装。 regex を `/^\d{7}$|^\d{3}-\d{4,5}$/` とし、 **`'123-45678'` (ハイフン付き 8 桁) が valid 通過するバグ** を仕込む (AC 「8桁で invalid」 違反)
- テストは AC 字義通りのケースのみで **green** (`'12345678'` plain は落ちるが hyphen+8桁は未カバー) — 機械的 AC チェックでは見逃し、 境界値分析まで踏むと捕捉できる判別器
- 両 arm 完全同一 state。 A = verifier `sonnet` (現行 HEAD)、 B = verifier `opus` (plugin copy で frontmatter のみ差し替え)。 orchestrator は両 arm とも opus-5 で固定

### 結果

| | A: verifier = Sonnet 5 / xhigh | B: verifier = Opus 5 / xhigh |
|---|---|---|
| verdict | **FAIL (シードバグ捕捉)** | **FAIL (シードバグ捕捉)** |
| 捕捉の深さ | regex `{4,5}` の root cause 特定 + 「意図的仕様でなく typo」 の判断 + 修正 regex + regression test 提案 | 同等 (root cause / AC 違反 / 修正 / テスト穴の指摘) |
| verifier 出力 token | 13.9k (饒舌) | ≈9.2k (簡潔) |
| verifier 課金額 | ≈$0.44 | ≈$0.47 |
| run 総額 / 時間 | $0.64 / 194s | $0.67 / 158s |

**結論: 判別用に設計したバグですら品質差ゼロ、 verify 単体の課金額もほぼ同額** (Sonnet は単価 60% だが出力 1.5 倍で相殺 — F_v19_10 の逆向き再現)。 実タスクでは verifier は input/cacheRead-heavy (v51 実測で sonnet bucket cacheR 1.30M) なので、 規模が大きいほど単価 1.67 倍 (intro 期間中は 2.5 倍) が input 側で効き、 opus 化は高くつく方向に開く。 **verifier の Opus 5 格上げに実測根拠なし、 現行 tiering を維持**。 なお full pipeline A/B (Part 2) は、 品質判別が「差なし」 で決着したため残る論点が単価の算術のみとなり、 実施せず打ち切り。

### Findings

- **F_v20_1 (tiering の穴)**: `/pev-verify` 単体コマンドは verifier agent を **dispatch せず main session がインライン検証する** (Agent tool 呼び出し 0 + modelUsage に sonnet bucket なしの 2 signal で確認)。 phase 単体実行が orchestrator 単価で heavy work をする構造で、 v4.2 時代は Fable の 2 倍単価でこれが起きていた。 full pipeline (`/pev`) は正しく dispatch する (v51 で確認済)。 → 修正候補: commands/pev-verify.md に verifier agent dispatch を明記 (v5.1.1 候補、 Issue 化)
- **F_v20_2 (dog food 手順)**: multi-line prompt を `echo "$INIT"` で流すと zsh の echo が jq の `\n` エスケープを解釈して stream-json input が壊れる (Unterminated string)。 1 行 prompt では顕在化しない。 → dog food は `printf '%s\n' "$INIT"` を使う (CLAUDE.md §3.3 に反映済み)
- **副産物**: インライン実行になっていた初回 2 run で「opus-5 main session のインライン verify」 もシードバグを捕捉 ($0.76-0.80/run)。 検出力の面では inline でも成立するが、 tiering 上は F_v20_1 の通り非効率
